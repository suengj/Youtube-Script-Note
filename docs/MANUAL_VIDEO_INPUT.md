# Individual YouTube video input

## Owner steps

In the **YT Link** tab, paste each individual YouTube video URL in column B under the `URL` header. Leave both `Source` (column D) and `Download 여부` (column E) empty for a new candidate; a non-empty value in either cell marks that video processed. A batch automatically imports eligible video IDs into `<DATA_ROOT>/input_df.csv` when `P03_SHEET_IMPORT_ENABLED=1`; the default is `0` (off). Set `P03_SHEET_IMPORT_SINCE=YYYY-MM-DD` to limit batch import to rows whose `Updated/Published Time/` date is on or after that date. If it is missing or invalid, the batch logs a warning and skips sheet import while continuing. `P03_SHEET_IMPORT_MAX` limits each run to the newest eligible rows and defaults to `5`. The normal batch queue then picks them up in that run. The import runs under the existing batch run lock. If the service-account key is missing or sheet import fails, the batch logs a warning and continues with its existing queues.

Before enabling imports or manual queueing, build `<DATA_ROOT>/processed_videos.csv` with `python scripts/build_processed_registry.py --data-root "$DATA_ROOT"`. The append-only registry has columns `video_id, first_seen_at, sources, last_status, model`; `sources` is a semicolon-separated list. It merges every ID in `output_df_new.csv` regardless of status, marked `YT Link` rows where `Source` or `Download 여부` is set, and successful or `skipped_historical` manual ledger rows. Use `--no-sheet` to build from local files only, or `--dry-run` to print counts by source without writing. Rebuilds preserve prior IDs. Without this file, sheet import and manual queue admission fail closed and log a warning. Each verified manual or channel success adds its ID atomically.

Any matching video ID with a non-empty `Source` or `Download 여부` cell on any Sheet row is processed, and missing registry entries are repaired with source `sheet_marked`. It preserves existing `input_df.csv` rows and appends only new video IDs, retaining date/title/source where those columns exist.

## Processing, retries, and sheet status

Before queueing `input_df.csv`, the batch applies `P03_MANUAL_SINCE=YYYY-MM-DD` to its `date` column. Dates in `YYYY.M.D` and `YYYY-MM-DD` form are accepted; rows before the cutoff and rows with missing or unparseable dates are skipped. If `P03_MANUAL_SINCE` is unset or invalid, the batch logs a warning and admits only rows marked `manual_imported=true` by the sheet importer. Existing rows without that marker are not admitted in this fallback mode. The sheet importer adds the marker to new rows it appends.

`P03_MANUAL_MAX` limits manual queue admission per batch, defaults to `5`, and accepts `0` to disable manual admissions. Eligible rows are sorted newest date first with stable tie-breakers; rows after the cap remain in `input_df.csv` and do not get new ledger entries. This cap is separate from `P03_SHEET_IMPORT_MAX`, which limits how many rows the importer appends from the Sheet.

When the batch loads the manual ledger, any `processing` entry whose corresponding `input_df.csv` row predates the cutoff is retained as terminal status `skipped_historical` with reason `historical input_df row before manual cutoff; owner: already processed`. Its attempt count is unchanged. A `skipped_historical` ID is recorded in the processed registry and is never admitted again, even if the cutoff later moves earlier or the ID returns in `input_df.csv` or the Sheet; it is excluded from both manual and channel candidate queues. Existing `deferred_backfill` entries are migrated to `skipped_historical` when the ledger is loaded. Successful ledger entries are left unchanged. A video is treated as processed when it appears in `processed_videos.csv` or any matching Sheet row has a non-empty `Source` (column D) or `Download 여부` (column E) value. Sheet markers missing from the registry are repaired with source `sheet_marked`. If the Sheet cannot be read, queue checks use the registry only. The manual queue is deduplicated by normalized video ID and merged with channel candidates, which retain channel metadata and policy. Failures, unsupported URLs, and policy skips remain in the local `data/manual_input_status.csv` ledger and are never written to the sheet. The retry limit is `CRAWL_QUEUE_MAX_RETRIES`.

At batch end, the system makes a best-effort daily backup of `processed_videos.csv` at `<YT_summary Drive root>/_p03_state/processed_videos/processed_videos_YYYYMMDD.csv` using the KST date. It verifies the copied bytes by SHA-256 and retains the latest 14 dated copies in that folder. Backup failure is logged as a warning and does not fail the batch. To restore, copy the latest verified CSV from that folder to `<DATA_ROOT>/processed_videos.csv`.

A manual ledger entry becomes `success` only after final Markdown is published and verified by the configured Drive publisher. If a publish falls back to local staging, the ledger stays `retryable_failed` with `pending_drive`; the next run reuses the staged Markdown only when its SHA-256 matches the ledger, keeps it until exact destination readback succeeds, and otherwise returns the item to normal pipeline reprocessing. Channel-crawl staging behavior is unchanged.

Manual items follow the same existing policies as channel items by default. When YouTube duration metadata is available, the Shorts duration filter applies; a filtered item is recorded as `skipped_policy` with its threshold reason in the ledger and is never written to the Sheet. If the video's channel is registered in `channel_df.csv` and its `auto_sub_only` flag is enabled, the downloader proceeds when accepted uploader or automatic captions exist and skips only when neither exists. Missing policy metadata does not invent a policy decision. Manual policy lookup reads the same `DATA_ROOT/channel_df.csv` registry used by channel discovery.

After the batch, successful and Drive-verified ledger rows with `sheet_synced=false` and no owner hold are written back. For each item, the writer snapshots every row's row number, exact `URL` text, normalized video ID, `Source`, and `Download 여부`. It writes every row matching the target video ID, setting `Source` to `own` only where that row's source was blank. It then reads the rows again. When row number, URL text, and video ID are unchanged, changed non-target cells are repaired by row. If that sequence changed, a non-target row is repaired by video ID only when that ID appears exactly once in both snapshots. Duplicate or missing IDs are left untouched when their row identity is ambiguous. Any detected anomaly records `sheet_synced=false`, `needs_manual_check=true`, a ledger reason, and an error log even if repair succeeded. An owner must clear `needs_manual_check` before a later run can write that item. A clean pass sets `sheet_synced=true` only when the row sequence is identical, every target row matches its expected values, and every non-target row is unchanged. Google Sheets has no compare-and-set, so a concurrent edit after final readback remains a residual race. Formula columns and all other cells are untouched.

Manual staged Markdown is published only when its SHA-256 matches the ledger. A missing or mismatched stage is moved to `WORK_PATH/quarantine/manual_staging/` and excluded from the batch flush scan. Regeneration uses `regen_attempts` independently of the ordinary pipeline retry count, with a cap of two; after the cap the ledger reason is `regen cap reached`.
